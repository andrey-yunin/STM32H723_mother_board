## 1. Обзор архитектурных изменений

### Что было (до Фазы 8.B+C)

```
ExecuteStep()
  ├─ Формирует CAN-кадр (заглушка)
  ├─ pending_actions_count--          ← мгновенный декремент
  └─ return

JobManager_Run()
  └─ Проверка таймеров WAIT_MS и таймаутов (неглубокий стек)
```

`ExecuteStep()` сам декрементировал `pending_actions_count` для каждого действия — CAN-ответов не ждал.
Цепочка вызовов была неглубокой, стек task_jobs_monitor = 128×4 = 512 байт хватал.

### Что стало (после Фазы 8.B+C)

```
task_can_handler (приоритет High1)
  └─ xQueueReceive(can_tx_queue) → ExecutorSim_ProcessTxMessage()
       └─ xQueueSend(can_rx_queue, DONE-ответ)

task_jobs_monitor (приоритет Low)
  └─ JobManager_Run()
       ├─ xQueueReceive(can_rx_queue)      ← НОВОЕ: чтение CAN RX
       └─ ProcessExecutorResponse()         ← НОВОЕ: вызывается из Run()
            └─ ExecuteStep()
                 └─ Dispatcher_SendUsbResponse()
                      └─ send_packet_to_queue()   ← ~260 байт на стеке
```

`pending_actions_count--` убран из ExecuteStep для CAN-действий.
Декремент теперь происходит в `ProcessExecutorResponse()` по получению DONE от исполнителя.
Цепочка вызовов стала глубокой — 4 уровня вложенности.

### Затронутые файлы

| Файл | Изменение |
|------|-----------|
| `App/Inc/Dispatcher/executor_simulator.h` | Новый файл |
| `App/Src/Dispatcher/executor_simulator.c` | Новый файл |
| `App/Src/Tasks/task_can_handler.c` | Вызов имитатора, HAL FDCAN закомментирован |
| `App/Src/Dispatcher/job_manager.c` | Run() читает CAN RX, убраны 7 декрементов |
| `Core/Src/main.c` | Стек task_jobs_monitor: 128→768 (×4) |

## 2. Проблема 1: USB CDC пропадает после прошивки

### Симптомы

- После компиляции и прошивки устройство не определяется как USB CDC
- В `lsusb` виден только ST-Link, нет ACM-устройства
- Плата не отвечает на USB-команды
- Перепрошивка не помогает — проблема воспроизводится стабильно

### Ложные гипотезы (отброшены)

1. **HAL_FDCAN без трансивера** — предположили, что `HAL_FDCAN_AddMessageToTxFifoQ()` без физического CAN-трансивера вызывает bus-off ошибки и крашит систему.
   - Закомментировали весь HAL FDCAN код
   - **Не помогло** — USB CDC по-прежнему пропадал
   - Вывод: FDCAN ошибки не влияют на USB-подсистему

2. **Ошибка в логике нового кода** — перепроверили все изменения в job_manager.c, executor_simulator.c, task_can_handler.c.
   - Код корректен, ошибок нет
   - Вывод: проблема не в логике, а в ресурсах

### Корневая причина: переполнение стека task_jobs_monitor

Новая цепочка вызовов потребляет значительно больше стека, чем старая:

```
JobManager_Run()                         ~550 байт
  ├─ rx_msg (CAN_Message_t)              16 байт
  ├─ response (CAN_Response_t)           16 байт
  ├─ err_msg[128]                        128 байт
  ├─ циклы, локальные переменные         ~50 байт
  ├─ контекст вызова (LR, сохр. регистры) ~40 байт
  │
  └─ ProcessExecutorResponse()           ~540 байт
      ├─ log_msg[128]                    128 байт
      ├─ resp_buf[128]                   128 байт
      ├─ указатели, индексы              ~40 байт
      ├─ контекст вызова                 ~40 байт
      │
      └─ ExecuteStep()                   ~600 байт
          ├─ tx_msg (CAN_Message_t)      16 байт
          ├─ log_buf[128]                128 байт
          ├─ resp_buf[128]               128 байт
          ├─ switch-case переменные      ~50 байт
          ├─ контекст вызова             ~40 байт
          │
          └─ send_packet_to_queue()      ~260 байт
              └─ tx_packet (USB_TxPacket_t) ~260 байт

ИТОГО данных:                            ~1950 байт
FreeRTOS overhead (TCB, guard):          ~300 байт
═══════════════════════════════════════
ВСЕГО:                                   ~2250 байт
```

Стек 128×4 = 512 байт → переполнение на ~1700 байт.

### Почему переполнение стека убивает USB CDC

Стек FreeRTOS-задачи растёт «вниз» (от конца выделенного блока к началу).
При переполнении стек перезаписывает соседние области памяти:

```
┌─────────────────────┐ высокий адрес
│  Стек task_jobs_mon  │
│  (растёт вниз ↓)    │
├─────────────────────┤ ← граница стека (512 байт от начала)
│                     │
│  ▼▼▼ ПЕРЕПОЛНЕНИЕ ▼▼▼│ ← перезапись чужой памяти
│                     │
├─────────────────────┤
│  USB CDC структуры  │ ← повреждены!
│  (USBD_HandleTypeDef│
│   PCD буферы, etc.) │
└─────────────────────┘ низкий адрес
```

Повреждённые USB-структуры приводят к тому, что:
- USB CDC endpoint не инициализируется
- Дескрипторы устройства содержат мусор
- Хост (ПК) не может провести enumeration
- Устройство не появляется как /dev/ttyACMx

### Хронология попыток

| Попытка | Стек | Результат | Почему |
|---------|------|-----------|--------|
| 1 | 128×4 = 512 | USB CDC пропал | Переполнение ~1700 байт |
| 2 | 256×4 = 1024 | USB CDC пропал | Переполнение ~1200 байт |
| 3 | 512×4 = 2048 | Работает! | Запас ~200 байт (на грани) |
| 4 | 768×4 = 3072 | Стабильно | Запас ~800 байт |

### Решение

**Файл:** `Core/Src/main.c`, строка 92 (атрибуты task_jobs_monitor)

```c
// БЫЛО:
.stack_size = 128 * 4,

// СТАЛО:
.stack_size = 768 * 4,
```

### Правило на будущее

> При добавлении новых вызовов в цепочку `JobManager_Run()` — пересчитывать глубину стека.
> Каждый буфер `char msg[128]` на любом уровне вложенности добавляет 128+ байт.
> Формула: **сумма всех локальных переменных на всех уровнях вложенности + 300 байт FreeRTOS overhead**.

## 3. Проблема 2: DISPENSER_WASH зависает на шаге 2

### Симптомы

- Команда INIT проходит успешно
- DISPENSER_WASH (0x2000) зависает с таймаутом на шаге 2
- Шаг 0 (ROTATE_MOTOR) и шаг 1 (ROTATE_MOTOR) выполняются нормально
- Шаг 2 содержит **два действия**: `ACTION_START_PUMP` + `ACTION_WAIT_MS`

### Лог ошибки

```
INFO: Job #3: Executing step 2 (2 actions).
DEBUG: Job #3: Sent START_PUMP (ID:1) to Exec.
DEBUG: Job #3: Started WAIT_MS for 10000 ms.
WARNING: Job #3: Step 2 timed out! Aborting.
```

### Корневая причина: WAIT_MS не декрементирует pending_actions_count

При реализации Фазы 8.C мы убрали `pending_actions_count--` из **всех** действий в `ExecuteStep()`,
включая `ACTION_WAIT_MS`. Но WAIT_MS — это **локальное** действие (таймер внутри дирижера),
для него **нет CAN-ответа DONE**.

#### Разбор по шагам

Шаг 2 рецепта `g_recipe_dispenser_wash`:
```
actions[0] = ACTION_START_PUMP   (CAN-команда → ждём DONE)
actions[1] = ACTION_WAIT_MS      (локальный таймер → НЕ ждём DONE)
```

При выполнении `ExecuteStep()`:
```
pending_actions_count = 2  (num_actions)

ACTION_START_PUMP  → отправляет CAN → НЕ декрементирует (правильно, ждём DONE)
ACTION_WAIT_MS     → запускает таймер → НЕ декрементирует (НЕПРАВИЛЬНО!)

pending_actions_count = 2
```

Приходит DONE от помпы:
```
ProcessExecutorResponse() → pending_actions_count-- → теперь 1
```

Но для WAIT_MS DONE никогда не придёт → `pending_actions_count` навсегда остаётся 1 → шаг не завершается → таймаут.

#### Почему проверка таймера в Run() тоже не спасала

В `JobManager_Run()` есть проверка таймера WAIT_MS:

```c
if (step->num_actions == 1 && step->actions[0].type == ACTION_WAIT_MS)
```

Это условие срабатывает **только** для «чистых» WAIT_MS-шагов (где единственное действие — ожидание).
В смешанном шаге `num_actions == 2` → условие **FALSE** → таймер не проверяется.

### Решение

Вернуть `pending_actions_count--` для `ACTION_WAIT_MS` в `ExecuteStep()`.

**Файл:** `App/Src/Dispatcher/job_manager.c`, в блоке `case ACTION_WAIT_MS:`

```c
case ACTION_WAIT_MS:
{
    uint32_t wait_ms = action->params.wait_time_ms;
    job->wait_timer_start = xTaskGetTickCount();
    job->wait_timer_duration = pdMS_TO_TICKS(wait_ms);
    job->wait_timer_active = true;
    job->pending_actions_count--;    // ← ВОССТАНОВИТЬ! Локальное действие, DONE не будет.
    // ...
    break;
}
```

### Классификация действий

| Тип действия | Отправляет CAN? | Декремент в ExecuteStep? | Кто завершает? |
|---|---|---|---|
| ACTION_ROTATE_MOTOR | Да | **Нет** | DONE от исполнителя |
| ACTION_START_PUMP | Да | **Нет** | DONE от исполнителя |
| ACTION_STOP_PUMP | Да | **Нет** | DONE от исполнителя |
| ACTION_HOME_MOTOR | Да | **Нет** | DONE от исполнителя |
| ACTION_START_MIXING_MOTOR | Да | **Нет** | DONE от исполнителя |
| ACTION_STOP_MIXING_MOTOR | Да | **Нет** | DONE от исполнителя |
| ACTION_PERFORM_SCAN | Да | **Нет** | DONE от исполнителя |
| **ACTION_WAIT_MS** | **Нет** | **Да** | Таймер в Run() |

### Правило на будущее

> При добавлении нового типа действия — определить: это CAN-команда или локальная операция?
> - CAN-команда → убрать `pending_actions_count--`, ждать DONE
> - Локальная операция → оставить `pending_actions_count--`, завершается немедленно

## 4. Проблема 3: GET_STATUS таймаут в комбинированном сценарии

### Симптомы

- Индивидуальные тесты (INIT, DISPENSER_WASH, SAMPLE_ROTATE и т.д.) проходят
- В комбинированном сценарии (8+ команд подряд) последний GET_STATUS не отвечает
- Таймаут при ожидании DATA/DONE
- Плата продолжает работать, но USB-ответы «теряются»

### Корневая причина: стек 512×4 на грани

При стеке 512×4 = 2048 байт запас составлял ~200 байт. При последовательном выполнении
множества команд стек «дышит» — глубина немного варьируется в зависимости от:

- Длины `snprintf`-форматирования (разная длина строк для разных команд)
- Количества DONE-ответов в очереди за один вызов `Run()`
- Выравнивания стека компилятором (padding)

При неблагоприятном стечении ~200 байт запаса не хватало → микропереполнение → повреждение
одной-двух переменных → непредсказуемое поведение USB.

### Решение

Увеличить стек до 768×4 = 3072 байт (запас ~800 байт). См. [Проблема 1](#2-проблема-1-usb-cdc-пропадает-после-прошивки).

## 5. Проблема 4: Полный зависон платы при повторном запуске

### Симптомы

- При повторном запуске теста (без перепрошивки) плата полностью зависает
- USB CDC соединение устанавливается очень медленно (~10 секунд вместо мгновенно)
- Первая же команда (INIT) не получает ответа
- Плата не восстанавливается, требуется аппаратный сброс

### Корневая причина: кумулятивное повреждение памяти

Это продолжение Проблемы 3. При стеке 512×4 = 2048:

1. **Первый запуск теста:** микропереполнения повреждают несколько байт → GET_STATUS не отвечает,
   но основная функциональность работает
2. **Между запусками:** повреждённые данные остаются в памяти (RAM не очищается при soft reset)
3. **Второй запуск:** новые переполнения накладываются на уже повреждённую память → USB CDC
   полностью неработоспособен

#### Механизм повреждения USB

```
Переполнение стека task_jobs_monitor
         │
         ▼
Перезапись USBD_HandleTypeDef / PCD буферов
         │
         ├─ dev_state = мусор → USB enumeration не проходит
         ├─ ep0_state = мусор → Control Transfer не работает
         └─ CDC Line Coding = мусор → хост не может настроить порт
         │
         ▼
USB CDC не отвечает → зависон
```

### Решение

Стек 768×4 = 3072 байт устраняет все переполнения. Все тесты проходят стабильно,
включая повторные запуски без перепрошивки.

### Диагностическая подсказка

> Если USB CDC «пропадает» или «зависает» после изменений в коде —
> **первым делом проверить стеки всех задач FreeRTOS**.
> Переполнение стека — самая частая причина необъяснимых крашей в STM32 + FreeRTOS.

Способы диагностики переполнения стека:
1. **FreeRTOS Stack High Water Mark:** `uxTaskGetStackHighWaterMark(NULL)` — возвращает
   минимальный оставшийся стек в словах. Если < 50 слов — опасно.
2. **configCHECK_FOR_STACK_OVERFLOW = 2** в `FreeRTOSConfig.h` — FreeRTOS вызовет
   `vApplicationStackOverflowHook()` при обнаружении переполнения.
3. **Паттерн 0xA5A5A5A5:** FreeRTOS заполняет стек этим паттерном при создании задачи.
   Можно проверить в отладчике, сколько байт осталось нетронутыми.

## 7. Чек-лист для будущих изменений

### При добавлении нового кода в цепочку JobManager

- [ ] Посчитать размер всех локальных переменных (особенно `char buf[128]`)
- [ ] Пересчитать суммарную глубину стека
- [ ] Убедиться, что запас стека > 500 байт
- [ ] Если запас < 500 байт — увеличить стек в `main.c`

### При добавлении нового типа действия (ActionType)

- [ ] Определить: CAN-команда или локальная операция?
- [ ] CAN-команда → **НЕ** декрементировать `pending_actions_count` в `ExecuteStep`
- [ ] Локальная операция → **ДЕКРЕМЕНТИРОВАТЬ** `pending_actions_count` в `ExecuteStep`
- [ ] Добавить в таблицу классификации (раздел 3)

### При переходе на реальный CAN

- [ ] Раскомментировать HAL FDCAN код в `task_can_handler.c`
- [ ] Закомментировать вызов `ExecutorSim_ProcessTxMessage()`
- [ ] Стек task_jobs_monitor **НЕ уменьшать** — цепочка вызовов та же
- [ ] Добавить таймаут в `osSemaphoreAcquire(usb_tx_semHandle, ...)` в `task_usb_handler.c`
- [ ] Добавить лимит ретраев для `CDC_Transmit_HS()` в `task_usb_handler.c`

### Диагностика USB CDC проблем

1. USB CDC пропал → проверить стеки всех задач
2. USB CDC медленный → проверить `osSemaphoreAcquire` без таймаута
3. USB CDC зависает периодически → проверить `configCHECK_FOR_STACK_OVERFLOW`
4. USB CDC не восстанавливается → аппаратный сброс (soft reset не очищает RAM)
