## 3. Фаза 3: Рефакторинг и решение архитектурных задач (Дата: Вторник, 3 февраля 2026 г.)

После успешного завершения Фазы 2 и детального анализа документации (`Commands_API`) были выявлены архитектурные пробелы, которые необходимо устранить перед массовым добавлением новых команд. Эта фаза направлена на создание масштабируемого фундамента.

### **3.1. Главная задача: Передача параметров в рецепты**

**Концепция решения: "Выделенный Парсер Параметров"**

**Главная цель: Обработка динамических параметров команд пользователя для атомарных команд.**

Идея заключается в том, чтобы централизовать всю логику разбора параметров в одном месте, но вынести ее из `command_parser.c` для чистоты архитектуры и обеспечить масштабируемость для динамически изменяемых параметров.

1.  **Новый модуль `parameter_parser`**: Создается новый модуль (`parameter_parser.c` и `.h`), который будет отвечать исключительно за разбор параметров пользовательской команды.
2.  **Функция `Parameters_Parse`**: Внутри этого модуля создается одна функция, например `void Parameters_Parse(UniversalCommand_t* cmd, ...)` которая содержит `switch (cmd->command_code)`. Эта функция будет брать сырые байты параметров из `UniversalCommand_t` и преобразовывать их в структурированные формы (например, `ParsedArgs_Init`, `ParsedArgs_DispenserWash`), заполняя соответствующие поля в `cmd->args` и устанавливая `cmd->args_type = ARGS_TYPE_PARSED`.
3.  **Единая точка входа**: `Parser_ProcessBinaryCommand` после нахождения команды в таблице и отправки `ACK` вызывает `Parameters_Parse`, передавая ей `UniversalCommand_t` для заполнения разобранными параметрами.
4.  **Связь с `AtomicAction_t` через `ParamSource_t`**: После того как `UniversalCommand_t` будет заполнена разобранными параметрами, `JobManager` будет использовать эти данные. `AtomicAction_t` теперь включает поле `ParamSource_t` для каждого своего параметра, которое указывает, откуда брать значение: либо из статического определения рецепта, либо из динамически полученных и разобранных параметров (`UniversalCommand_t`) пользовательской команды (например, `PARAM_SOURCE_CMD_INIT_MASK`, `PARAM_SOURCE_CMD_DISPENSER_VOLUME`). Это обеспечивает гибкость и позволяет рецептам использовать параметры, предоставленные пользователем.

**Преимущества:**
*   **Четкое разделение ответственности**: `command_parser` идентифицирует команду, `parameter_parser` разбирает ее параметры, а `JobManager` исполняет рецепт, используя уже готовые, структурированные параметры.
*   **Высокая масштабируемость**: Добавление новой параметризованной команды требует лишь добавления соответствующего `case` в `switch` в `parameter_parser.c` и обновления `UniversalCommand_t`, без изменения ядра `JobManager` или `command_parser.c`.
*   **Улучшенная читаемость и обслуживаемость**: Вся логика парсинга находится в одном выделенном файле, что упрощает ее поиск, понимание и модификацию.
*   **Гибкость рецептов**: `ParamSource_t` позволяет рецептам быть более универсальными, адаптируясь к динамическим входным данным от пользователя.
