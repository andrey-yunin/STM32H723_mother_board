# Отчет об архитектурных решениях: Интеграция Экосистемы DDS-240
**Дата:** 9 апреля 2026 г.  
**Статус:** Ревизия 1.4 (Кумулятивная, Успешное внедрение иерархии)

## 1. Резюме аудита и выявленные "Швы"
Проведен анализ трех уровней взаимодействия (Host <-> Conductor <-> Executor). Были выявлены критические разрывы в протоколах:
*   **Транспорт:** Переменный DLC (3-8) в старой версии Дирижера приводил к нестабильности bxCAN на исполнителях.
*   **Адресация:** Использование глобальных ID (140+) мешало модульности.
*   **Endianness:** Разрыв между Big-Endian (Хост) и Little-Endian (Исполнители).

---

## 2. Утвержденные архитектурные решения (Реализовано)

### 2.1. Концепция «Умного Шлюза» (Smart Gateway)
Дирижер берет на себя роль активного транслятора:
*   **Трансляция ID:** Прозрачный перевод логического `SYS_ID` в пару `(NodeID, Channel)`.
*   **Трансляция Endianness:** Конвертация данных (LE <-> BE) для обеспечения бесшовности.
*   **Унификация транспорта:** Строгий переход на **DLC=8** для всех исходящих CAN-команд.

### 2.2. Иерархия Маппинга (System vs Device)
Для гибкости системы внедрено разделение:
1.  **System Level (`system_mapping.h`):** Определяет роли (Дозаторы, Диски, Насосы). Использует префикс `SYS_`.
2.  **Device Level (`device_mapping.h/.c`):** Описывает физику CAN (NodeID 0x20, 0x30, 0x40 и индексы 0-15).

## 4. Маршрутизация ответов и транзакций

### 4.1. Статусы (ACK/NACK)
*   Дирижер принимает 4-байтовый ACK/NACK от исполнителя.
*   Сопоставляет его с активным `Job_ID`.
*   Транслирует результат Хосту в формате `CM>`.

### 4.2. Данные (DATA - Температура)
*   Исполнитель присылает `int16_t` (0.1°C) в Little-Endian.
*   **Решение:** Дирижер переставляет байты (LE -> BE) перед отправкой Хосту для соответствия `protocol.md`.

Фундамент для бесшовной интеграции заложен. Дирижер теперь корректно "видит" физическую топологию исполнителей, скрывая её от верхнего уровня.

## 7. Ревизия 1.5 (13 апреля 2026 г.): Унификация Ответного Слоя (Response Layer)
**Статус:** Согласовано, переход к реализации.

### 7.1. Архитектурное решение: Единый шаблон ответа (Executor -> Conductor)
Для обеспечения полной совместимости с тремя проектами исполнителей (Motion, Fluidic, Thermo) и исключения «костылей», утвержден следующий стандарт расположения данных в CAN-кадре ответа:

#### Тип 0x01 (ACK) / 0x02 (NACK)
*   data[0-1]: cmd_code (LE) — Код команды, на которую отвечаем.
*   data[2-3]: error_code (LE) — Для ACK всегда 0, для NACK коды 0x0001-0x0007.

#### Тип 0x03 (DATA / DONE / LOG)
*   data[0]: sub_type (0x01=DONE, 0x02=DATA, 0x03=LOG).
*   data[1-2]: cmd_code (LE) — Код команды-инициатора.
*   data[3]: ch_idx — Физический индекс канала (0-15). Строго закреплен в 3-м байте.
*   data[4-7]: payload — Полезная нагрузка (например, 4 байта данных для DATA).

### 7.2. Обоснование (Advanced Level)
1.  **Прозрачность транзакций**: Наличие cmd_code в каждом ответе DATA/DONE позволяет Дирижеру мгновенно сопоставлять асинхронное событие с активным Job_ID без сложного поиска в очередях.
2.  **Универсальность**: Дирижер больше не делит ответы на «температурные» или «двигательные» на уровне парсера — он видит универсальный контейнер данных.
3.  **Бесшовность**: Использование 32-битного контейнера в DATA позволяет передавать любые значения (от int16_t температуры до int32_t координат шаговых двигателей) без изменения кода парсера.

## 8. Ревизия 1.6 (13 апреля 2026 г.): Промышленный стандарт Discovery (Этап 2.4)
**Статус:** Проектирование и переход к реализации.

### 8.1. Концепция Паспортизации Сети (Full Discovery)
Вместо упрощенного "пинга", Дирижер внедряет трехфазный протокол идентификации узлов:
1.  **Broadcast Scan (0xF001)**: Опрос всех устройств на шине для получения их типов (Motion/Fluidic/Thermo) и версий FW.
2.  **UID Identification (0xF004)**: Получение уникального 96-битного ID чипа для привязки физического контроллера к логической роли.
3.  **Address Enforcement (0xF005)**: Принудительное назначение NodeID в случае конфликтов или замены оборудования.

### 8.2. Интеграция с системной логикой
Процесс Discovery становится обязательным пре-реквизитом для команды INIT (0x1002). 
*   **Результат:** Дирижер строит DeviceInventory (Карту сети). Если инвентаризация не совпадает с требуемой маской модулей — выполнение блокируется с детальной ошибкой.
