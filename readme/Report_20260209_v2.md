## 2. Архитектурная концепция: Обработка команд

В основе системы лежит простая и мощная аналогия с кулинарией, которая помогает разделить ответственность между модулями.

*   **Ингредиенты (`AtomicAction_t`)**: Это самые простые, неделимые действия, которые может выполнить система.
*   **Шаги (`ProcessStep_t`)**: Это группа из одного или нескольких "ингредиентов", которые должны выполняться **одновременно (параллельно)**.
*   **Рецепты (массив `ProcessStep_t[]`)**: Это полная, упорядоченная последовательность шагов, необходимая для выполнения сложной задачи.
*   **Шеф-повар (`JobManager`)**: Это "мозг" системы, который выполняет рецепты.

### Параметризация рецептов: Фильтрующая логика

Проблема статических рецептов в том, что они негибкие. Команда `INIT`, например, должна уметь инициализировать как все модули сразу, так и только один выбранный. Здесь в игру вступает **"фильтрующая логика"**, позволяющая `JobManager` динамически пропускать действия в статическом рецепте на основе runtime-параметров.

## 3. Финальная архитектурная концепция (на Понедельник, 9 февраля 2026 г.)

Этот раздел описывает финальный, согласованный план по рефакторингу системы для поддержки параметризованных команд.

### **Концепция решения: "Выделенный Парсер Параметров с Трансляцией Параметров"**

**Главная цель: Обработка динамических параметров команд пользователя для атомарных команд, включая сложные преобразования.**

Идея заключается в том, чтобы централизовать всю логику разбора параметров в одном месте (`parameter_parser`), но вынести сложные расчеты и преобразования высокоуровневых параметров в низкоуровневые аппаратные инструкции в отдельный модуль (`param_translator`). Это обеспечивает чистоту архитектуры, масштабируемость и легкость тестирования.

1.  **Новый модуль `param_translator`**: Создается новый модуль (`param_translator.c` и `.h`), который будет отвечать за преобразование высокоуровневых параметров (например, номер кюветы) в низкоуровневые аппаратные действия (например, количество шагов мотора).
2.  **Модуль `parameter_parser`**: Теперь он отвечает за:
    *   Чтение сырых байтов из входящей команды.
    *   Вызов функций из `param_translator` для выполнения необходимых расчетов (например, `ParamTranslator_CuvetteToSteps(cuvette_number)`).
    *   Сохранение *рассчитанных, готовых к использованию* значений (например, `rotate_steps`) в структуру `ParsedArgs_WashStationWash`.
3.  **Функция `Parameters_Parse`**: Внутри `parameter_parser` эта функция берет сырые байты параметров из `UniversalCommand_t` и преобразовывает их в структурированные формы (например, `ParsedArgs_Init`, `ParsedArgs_DispenserWash`, `ParsedArgs_WashStationWash`), заполняя соответствующие поля в `cmd->args` и устанавливая `cmd->args_type = ARGS_TYPE_PARSED`. Важно, что здесь же происходит вызов функций `param_translator` для расчета производных параметров.
4.  **Единая точка входа**: `Parser_ProcessBinaryCommand` после нахождения команды в таблице и отправки `ACK` вызывает `Parameters_Parse`, передавая ей `UniversalCommand_t` для заполнения разобранными и рассчитанными параметрами.
5.  **Связь с `AtomicAction_t` через `ParamSource_t`**: После того как `UniversalCommand_t` будет заполнена разобранными и рассчитанными параметрами, `JobManager` будет использовать эти данные. `AtomicAction_t` теперь включает поле `ParamSource_t` для каждого своего параметра, которое указывает, откуда брать значение: либо из статического определения рецепта, либо из динамически полученных и рассчитанных параметров (`UniversalCommand_t`) пользовательской команды (например, `PARAM_SOURCE_CMD_INIT_MASK`, `PARAM_SOURCE_CMD_DISPENSER_VOLUME`, `PARAM_SOURCE_CMD_WASH_STATION_WASH_ROTATE_STEPS`). Это обеспечивает гибкость и позволяет рецептам использовать параметры, предоставленные пользователем, в уже подготовленном виде.

**Преимущества:**
*   **Четкое разделение ответственности**: `command_parser` идентифицирует команду, `parameter_parser` разбирает ее параметры и выполняет преобразования с помощью специализированных модулей (`param_translator`), а `JobManager` исполняет рецепт, используя уже готовые, структурированные параметры.
*   **Высокая масштабируемость**: Добавление новой параметризованной команды требует лишь добавления соответствующего `case` в `switch` в `parameter_parser.c` и обновления `UniversalCommand_t`, без изменения ядра `JobManager` или `command_parser.c`. Сложные расчеты выносятся в отдельные, тестируемые модули.
*   **Улучшенная читаемость и обслуживаемость**: Вся логика парсинга и расчета находится в выделенных файлах, что упрощает их поиск, понимание и модификацию.
*   **Гибкость рецептов**: `ParamSource_t` позволяет рецептам быть более универсальными, адаптируясь к динамическим входным данным от пользователя в уже подготовленном виде.

# Руководство: Как добавить новую команду-рецепт в проект

Это руководство описывает шаги, необходимые для добавления новой команды, выполняемой через `JobManager` как "рецепт".

## Шаг 1: Определение ID рецепта

Каждая новая команда-рецепт должна иметь уникальный идентификатор.

**Действие:**
1.  Откройте файл `App/Inc/Dispatcher/command_parser.h`.
2.  В перечислении (enum) `RecipeID_t` добавьте новый идентификатор для вашей команды перед `RECIPE_MAX_ID`.

**Пример:**
```c
typedef enum {
    // ... существующие ID ...
    RECIPE_DISPENSER_WASH,
    RECIPE_NEW_COMMAND, // <-- Ваша новая команда
    // --- [ADD_NEW_COMMAND] ---
    RECIPE_MAX_ID
} RecipeID_t;
```

## Шаг 2: Создание рецепта

Рецепт — это последовательность шагов (действий), которые должно выполнить устройство.

**Действие:**
1.  Откройте файл `App/Src/Dispatcher/recipe_store.c`.
2.  Создайте глобальную переменную `const ProcessStep_t[]` для вашего рецепта.

**Пример:**
```c
// Определение шагов для рецепта "Новая Команда"
const ProcessStep_t g_recipe_new_command[] = {
    // Пример: шаг 1 - вращать мотор, используя динамические параметры
    { .atomic_actions = (const AtomicAction_t[]){
        { .action = ACTION_ROTATE_MOTOR, .params.rotate_motor = {
            .motor_id = 0, .motor_id_source = PARAM_SOURCE_CMD_NEW_COMMAND_MOTOR_ID, // Динамический ID
            .steps = 0,    .steps_source = PARAM_SOURCE_CMD_NEW_COMMAND_STEPS,    // Динамические шаги
            .speed = 0,    .speed_source = PARAM_SOURCE_CMD_NEW_COMMAND_SPEED     // Динамическая скорость
        } } 
    }, .num_actions = 1 },

    // Пример: шаг 2 - задержка на 500 мс
    { .atomic_actions = (const AtomicAction_t[]){
        { .action = ACTION_WAIT_MS, .params.wait = { .delay_ms = 500, .delay_ms_source = PARAM_SOURCE_STATIC } }
    }, .num_actions = 1 },

    // Маркер конца рецепта
    { .atomic_actions = NULL, .num_actions = 0 }
};
```

**Важно:** Для динамических параметров, укажите соответствующий `ParamSource_t` (его нужно будет определить на следующем шаге) и установите статические значения (например, `.steps = 0`) в 0.

## Шаг 3: Определение источников параметров

Система должна знать, откуда брать динамические параметры для атомарных действий.

**Действие:**
1.  Откройте файл `App/Inc/Dispatcher/recipe_store.h`.
2.  В перечислении `ParamSource_t` добавьте новые константы для каждого динамического параметра вашей новой команды.

**Пример:**
```c
typedef enum {
    // ... существующие источники ...
    PARAM_SOURCE_CMD_DISPENSER_WASH_CYCLES,
    PARAM_SOURCE_CMD_WASH_STATION_WASH_CYCLES, // <-- Пример для существующей команды
    PARAM_SOURCE_CMD_WASH_STATION_WASH_ROTATE_STEPS, // <-- Новый источник для рассчитанных шагов поворота диска

    // --- Параметры для NEW_COMMAND ---
    PARAM_SOURCE_CMD_NEW_COMMAND_MOTOR_ID,
    PARAM_SOURCE_CMD_NEW_COMMAND_STEPS,
    PARAM_SOURCE_CMD_NEW_COMMAND_SPEED,

    PARAM_SOURCE_MAX
} ParamSource_t;
```

## Шаг 4: Регистрация рецепта

Система должна знать, как найти ваш новый рецепт по его ID.

**Действие:**
1.  Откройте файл `App/Src/Dispatcher/recipe_store.c`.
2.  В функции `Recipe_Get`, добавьте `case` в `switch` для вашего нового `RecipeID_t`.

**Пример:**
```c
const ProcessStep_t* Recipe_Get(RecipeID_t id) {
    switch (id) {
        // ... существующие case ...
        case RECIPE_DISPENSER_WASH:
            return g_recipe_dispenser_wash;
        case RECIPE_WASH_STATION_WASH: // <-- Пример для существующей команды
            return g_recipe_wash_station_wash;
        case RECIPE_NEW_COMMAND: // <-- Ваш новый case
            return g_recipe_new_command;
        default:
            return NULL;
    }
}
```
