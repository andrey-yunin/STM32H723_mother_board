## 2. Архитектурная концепция: Обработка команд

В основе системы лежит простая и мощная аналогия с кулинарией, которая помогает разделить ответственность между модулями.

*   **Ингредиенты (`AtomicAction_t`)**: Это самые простые, неделимые действия, которые может выполнить система.
*   **Шаги (`ProcessStep_t`)**: Это группа из одного или нескольких "ингредиентов", которые должны выполняться **одновременно (параллельно)**.
*   **Рецепты (массив `ProcessStep_t[]`)**: Это полная, упорядоченная последовательность шагов, необходимая для выполнения сложной задачи.
*   **Шеф-повар (`JobManager`)**: Это "мозг" системы, который выполняет рецепты.

### Параметризация рецептов: Фильтрующая логика

Проблема статических рецептов в том, что они негибкие. Команда `INIT`, например, должна уметь инициализировать как все модули сразу, так и только один выбранный. Здесь в игру вступает **"фильтрующая логика"**, позволяющая `JobManager` динамически пропускать действия в статическом рецепте на основе runtime-параметров.

## 3. Финальная архитектурная концепция (на Вторник, 3 февраля 2026 г.)

Этот раздел описывает финальный, согласованный план по рефакторингу системы для поддержки параметризованных команд.

### **Концепция решения: "Выделенный Парсер Параметров"**

**Главная цель: Обработка динамических параметров команд пользователя для атомарных команд.**

Идея заключается в том, чтобы централизовать всю логику разбора параметров в одном месте, но вынести ее из `command_parser.c` для чистоты архитектуры и обеспечения масштабируемости для динамически изменяемых параметров.

1.  **Новый модуль `parameter_parser`**: Создается новый модуль (`parameter_parser.c` и `.h`), который будет отвечать исключительно за разбор параметров пользовательской команды.
2.  **Функция `Parameters_Parse`**: Внутри этого модуля создается одна функция, например `void Parameters_Parse(UniversalCommand_t* cmd, ...)` которая содержит `switch (cmd->command_code)`. Эта функция будет брать сырые байты параметров из `UniversalCommand_t` и преобразовывать их в структурированные формы (например, `ParsedArgs_Init`, `ParsedArgs_DispenserWash`), заполняя соответствующие поля в `cmd->args` и устанавливая `cmd->args_type = ARGS_TYPE_PARSED`.
3.  **Единая точка входа**: `Parser_ProcessBinaryCommand` после нахождения команды в таблице и отправки `ACK` вызывает `Parameters_Parse`, передавая ей `UniversalCommand_t` для заполнения разобранными параметрами.
4.  **Связь с `AtomicAction_t` через `ParamSource_t`**: После того как `UniversalCommand_t` будет заполнена разобранными параметрами, `JobManager` будет использовать эти данные. `AtomicAction_t` теперь включает поле `ParamSource_t` для каждого своего параметра, которое указывает, откуда брать значение: либо из статического определения рецепта, либо из динамически полученных и разобранных параметров (`UniversalCommand_t`) пользовательской команды (например, `PARAM_SOURCE_CMD_INIT_MASK`, `PARAM_SOURCE_CMD_DISPENSER_VOLUME`). Это обеспечивает гибкость и позволяет рецептам использовать параметры, предоставленные пользователем.

**Преимущества:**
*   **Четкое разделение ответственности**: `command_parser` идентифицирует команду, `parameter_parser` разбирает ее параметры, а `JobManager` исполняет рецепт, используя уже готовые, структурированные параметры.
*   **Высокая масштабируемость**: Добавление новой параметризованной команды требует лишь добавления соответствующего `case` в `switch` в `parameter_parser.c` и обновления `UniversalCommand_t`, без изменения ядра `JobManager` или `command_parser.c`.
*   **Улучшенная читаемость и обслуживаемость**: Вся логика парсинга находится в одном выделенном файле, что упрощает ее поиск, понимание и модификацию.
*   **Гибкость рецептов**: `ParamSource_t` позволяет рецептам быть более универсальными, адаптируясь к динамическим входным данным от пользователя.

# Руководство: Как добавить новую команду-рецепт в проект

*(Примечание: Это руководство будет обновлено после завершения рефакторинга в Фазе 3, чтобы включить шаг по добавлению логики в `parameter_parser.c`)*

Это руководство описывает шаги, необходимые для добавления новой команды, выполняемой через `JobManager` как "рецепт".

## Шаг 1: Определение ID рецепта

Каждая новая команда-рецепт должна иметь уникальный идентификатор.

**Действие:**
1.  Откройте файл `App/Inc/Dispatcher/command_parser.h`.
2.  В перечислении (enum) `RecipeID_t` добавьте новый идентификатор для вашей команды перед `RECIPE_MAX_ID`.

**Пример:**
```c
typedef enum {
    // ... существующие ID ...
    RECIPE_INITIALIZE_SYSTEM,
    RECIPE_NEW_COMMAND, // <-- Ваша новая команда
    // --- [ADD_NEW_COMMAND] ---
    RECIPE_MAX_ID
} RecipeID_t;
```

## Шаг 2: Создание рецепта

Рецепт — это последовательность шагов (действий), которые должно выполнить устройство.

**Действие:**
1.  Откройте файл `App/Src/Dispatcher/recipe_store.c`.
2.  Создайте статический массив `ProcessStep_t`, описывающий шаги для вашего рецепта.
3.  Создайте глобальную переменную `const ProcessStep_t[]` для вашего рецепта.

**Пример:**
```c
// Определение шагов для рецепта "Новая Команда"
const ProcessStep_t g_recipe_new_command[] = {
    // Пример: шаг 1 - включить мотор 1 на 1000 тиков
    { .atomic_actions = (const AtomicAction_t[]){ { .action = ACTION_ROTATE_MOTOR, .params.rotate_motor = { .motor_id = 1, .motor_id_source = PARAM_SOURCE_STATIC, .steps = 1000, .steps_source = PARAM_SOURCE_STATIC, .speed = 500, .speed_source = PARAM_SOURCE_STATIC } } }, .num_actions = 1 },
    // Пример: шаг 2 - задержка на 500 мс
    { .atomic_actions = (const AtomicAction_t[]){ { .action = ACTION_WAIT_MS, .params.wait = { .delay_ms = 500, .delay_ms_source = PARAM_SOURCE_STATIC } } }, .num_actions = 1 },
    // Маркер конца рецепта
    { .atomic_actions = NULL, .num_actions = 0 }
};
```
**Важно:** Для добавления динамических параметров, не забудьте указать соответствующий `ParamSource_t` для каждого параметра, а также добавить необходимые поля `_source` в определения `AtomicAction_t` в `recipe_store.h`.

## Шаг 3: Регистрация рецепта

Система должна знать, как найти ваш новый рецепт по его ID.

**Действие:**
1.  Оставаясь в файле `App/Src/Dispatcher/recipe_store.c`, найдите функцию `Recipe_Get`.
2.  Добавьте `case` в `switch` для вашего нового `RecipeID_t`, который будет возвращать указатель на вашу глобальную переменную рецепта.

**Пример:**
```c
const ProcessStep_t* Recipe_Get(RecipeID_t id) {
    switch (id) {
        // ... существующие case ...
        case RECIPE_INITIALIZE_SYSTEM:
            return g_recipe_initialize_system;
        case RECIPE_NEW_COMMAND: // <-- Ваш новый case
            return g_recipe_new_command;
        default:
            return NULL;
    }
}
```

## Шаг 4: Регистрация бинарной команды

Теперь нужно связать код бинарной команды (например, `0x2000`) с вашим ID рецепта.

**Действие:**
1.  Откройте файл `App/Src/Dispatcher/command_parser.c`.
2.  В массиве `recipe_command_table` добавьте новый дескриптор `RecipeCommandDescriptor_t` для вашей команды.

**Пример:**
```c
const RecipeCommandDescriptor_t recipe_command_table[] = {
    // ... существующие дескрипторы ...
    {
        .command_code = 0x1002, // INIT
        .min_params_len = 1,
        .max_params_len = 1,
        .recipe_id = RECIPE_INITIALIZE_SYSTEM
    },
    {
        .command_code = 0x2000, // <-- Код вашей новой команды
        .min_params_len = 4,    // <-- Минимальная длина параметров
        .max_params_len = 4,    // <-- Максимальная длина параметров
        .recipe_id = RECIPE_NEW_COMMAND // <-- ID вашего рецепта
    },
};
```
**Важно:** Убедитесь, что `min_params_len` и `max_params_len` соответствуют документации на протокол для этой команды.
